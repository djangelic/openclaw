System Schema

Notion Schema + Data Contract

This is the actual structure the workflow should rely on inside Business Projects. Top-level rows act as parent project objects. Sub-items act as milestone objects.

The rule is simple: if a value needs to show up in an email, a Slack milestone announcement, or the internal payout email, it should come from this structure — not from freehand copy floating somewhere else.

Parent rows = projects

Use top-level rows for client projects like Convibe, CPLC, Jeff Cesare Realty, or marketing/video work.

Sub-items = milestones

Use sub-items for milestone-level updates, value unlocks, and distribution events.

Parent/child mapping rule
Client-facing onboarding and milestone emails should read from the parent project row for global project context, then read from one or more sub-items for milestone-specific progress and messaging.

Email mapping summary

Welcome / onboarding emailProject row only, plus milestone roadmap from related sub-items.
Milestone completion emailParent project row + one milestone sub-item + budget checkpoint fields.
Waiting on client emailParent project row + blocker/needs-input flags.
Owner payout emailParent project row + milestone value fields + distribution fields + Wave truth.

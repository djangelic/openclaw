⚠️ On MCP Authentication

ChatGPT's MCP implementation only supports OAuth. The n8n MCP Trigger node supports header auth or no auth. Running MCP with no authentication is essentially a verbose, self-describing webhook with zero protection. Go with header auth.

The Portability Principle — Own the Exit

The ability to walk away is what keeps vendors honest and keeps power with the client.

AI tooling is at exactly the same inflection point right now. If your tools are MCP servers you own, your AI is replaceable. If your tools are ChatGPT plugins, Claude Projects, or Gemini extensions — you're the one locked in.

MCP — The Portability Standard

MCP — Model Context Protocol — is an open standard that lets any AI model call external tools through a single, universal interface. Instead of building custom integrations for every AI provider, you build once and connect anywhere.

If you've used n8n before, you're used to integrations coming in pairs — a trigger and a node. One to receive, one to send. MCP is different. There's no MCP "node" in the traditional sense. Instead, that node is split into two pieces: the MCP Trigger receives calls from external AIs, and the MCP Tool lets your n8n agents call out to external MCP servers, acting as a client to them.

Same integration, two shapes, because AI workflows don't fit neatly into a single rectangle.

And sitting above both of them is what I'm calling the MCP Gateway — a newer, instance-level capability where your entire n8n deployment acts as a single MCP server with OAuth authentication. Flip a toggle in any workflow's settings, and it becomes available to external AI clients through one unified endpoint.

A note on naming: n8n officially calls these the "MCP Server Trigger node," the "MCP Client Tool node," and... well, the instance-level feature doesn't have a clean name yet. I think Gateway, Trigger, and Tool are clearer. If engineering is reading this — you're welcome.

The Three Layers

MCP Gateway

Instance-level • OAuth • One endpoint

Your entire n8n instance becomes a single MCP server. External AIs connect through one URL with OAuth authentication. Any workflow you toggle on becomes a tool the AI can call. This is the front door — the bouncer with the clipboard.

MCP Trigger

Workflow-level • Header auth • Granular control

A dedicated workflow that starts when an external AI calls in. You build the workflow, attach specific tools, and get a unique URL. More manual than the Gateway, but you control exactly what's exposed and how. This is the side door with its own lock.

MCP Tool

Sub-node • Attaches to AI agents • Outbound

The other direction. When you build an AI agent inside n8n and want it to use tools hosted on someone else's MCP server, you attach an MCP Tool. n8n becomes the client, reaching out instead of receiving.

Why This Matters for Portability

The Gateway and Trigger handle the receiving side — external AIs calling into n8n. The Tool handles the sending side — n8n's agents calling out. Together they're the complete MCP integration, split across two shapes because the two directions live in fundamentally different contexts.

The important part: n8n handles all the OAuth on the backend. Your AI connects to n8n with simple header auth or through the Gateway's OAuth. n8n connects to Google, Slack, Notion, and everything else using its own credentials. The AI never touches those tokens directly. Swap the AI, keep the tools. Swap the tools, keep the AI.

Update — February 19, 2026

It Already Happened

While I was writing this post, Anthropic proved the point for me. They just published an official legal and compliance page formally banning the use of Claude subscription OAuth tokens in any third-party tool — including their own Agent SDK.

Read that again. Anthropic banned their own SDK from using subscription credentials. If their own tools aren't exempt, nothing is.

Developers across OpenCode (107k+ GitHub stars), Roo Code, Cline, and dozens of other tools woke up to broken workflows overnight. No advance notice. No migration path. Just a server-side switch and a terse error message. The Hacker News thread is full of devs calling it "the AI equivalent of choosing Oracle over Postgres."

What This Means If You Use OpenClaw

The good news: OpenClaw users with API keys are completely unaffected. The ban targets subscription OAuth tokens being used outside Anthropic's own apps. If you're paying per token via the API Console, nothing changes.

The better news: this is exactly why portability matters. OpenClaw is model-agnostic. It works with any OpenAI-compatible endpoint. Today you run Claude. Tomorrow Anthropic changes their terms and you swap to DeepSeek V3.2 at a tenth of the cost. Your tools, your memory, your workflows — none of it changes. Only the model behind it does.

n8n: The Secret Weapon

Here's what most people are missing. Services like Google Calendar, Notion, and Slack all require OAuth for access. Normally that means your AI tool needs its own OAuth integration with each service — which is exactly the kind of vendor-specific plumbing that creates lock-in.

But when you put n8n in the middle, your AI never touches OAuth directly. It calls n8n through a simple MCP connection with header auth. n8n handles the OAuth on the backend. Your AI gets access to OAuth-protected services through a single, portable API layer. Swap the AI, keep the tools. Swap the tools, keep the AI.

Without n8n

With n8n

One connection. Swap the AI anytime. Tools don't notice.

Anthropic's ban is a warning shot. The next one might come from OpenAI, Google, or whoever else decides their ecosystem should be a walled garden. Build your tools so it doesn't matter when it happens.
